# Chapter 6: NASS and Grey-Box Coverage in Multi-Threaded Daemons

Extracting the interface definition of a proprietary HAL service via DGIE resolves the initial structural barrier. However, structural compliance is insufficient for discovering deep logical vulnerabilities. As system services increase in complexity, black-box generation techniques become less effective. Navigating the stateful logic underlying the deserialization stub necessitates evolutionary guidance. The fuzzer must observe which code paths are executed by specific inputs to iteratively refine mutations and explore deeper application states.

This evolutionary process is dependent on accurate code coverage feedback. In the context of Android native system services, collecting this feedback introduces a significant engineering challenge: the concurrency problem. This chapter examines how NASS addresses this issue, facilitating precise, grey-box fuzzing for multi-threaded Android daemons.

## 6.1 The Concurrency Problem in Android System Services

Traditional grey-box fuzzing assumes a deterministic execution environment: the fuzzer instantiates a single target process, supplies an input, and records the coverage generated by that isolated execution thread.

Android system services inherently violate this assumption. Daemons such as `cameraserver` or vendor HAL services do not execute in isolation. They are highly concurrent, multi-threaded processes operating continuously in the background. Concurrently with fuzzing, a service may process legitimate Binder requests from the Android framework, handle hardware interrupts, or execute internal maintenance routines.

Naively applying a coverage tracker to the entire HAL service process results in severe coverage pollution. The fuzzer is unable to distinguish basic blocks executed by its synthesized payloads from blocks executed by independent background threads processing normal OS traffic. This pollution disrupts the evolutionary algorithm's ability to correlate specific input mutations with discrete code paths, rendering coverage guidance ineffective.

## 6.2 Thread-Localized Tracing via Dynamic Binary Instrumentation

To extract precise coverage data, the fuzzer must isolate its execution footprint from the system's background activity. NASS achieves this through the targeted application of Dynamic Binary Instrumentation (DBI) utilizing the Frida framework, specifically leveraging the Frida Stalker engine.

NASS integrates coverage collection with the mechanics of Binder IPC, exploiting the Single Entry Point (Si) RPC principle. The isolation logic operates as follows:

When an IPC request triggers the target service's `onTransact` function, NASS's instrumentation hook intercepts the execution. The hook inspects the kernel-provided caller credentials to retrieve the Process ID (PID) of the requesting client. If the calling PID matches the NASS fuzzer client, the request is identified as a fuzzing payload. In this scenario, NASS activates Frida Stalker exclusively on the current executing thread. If the calling PID does not match, the transaction is recognized as legitimate OS traffic, and normal execution proceeds without instrumentation overhead.

Upon the termination of the `onTransact` function, the instrumentation hook deactivates Frida Stalker for that thread and exports the synchronous coverage bitmap to the fuzzer. 

By filtering execution traces based on PID, NASS ensures that the resulting coverage bitmap is perfectly isolated. The bitmap represents only the deterministic execution path triggered by the fuzzer's input, eliminating the multi-threaded background noise inherent to system daemons.

## 6.3 The Evolutionary Fuzzing Feedback Loop

With the interface dynamically mapped via DGIE and isolated coverage collection implemented via PID-filtered Stalker tracing, NASS establishes a robust evolutionary fuzzing loop.

NASS employs an interface-aware mutator integrated with LibFuzzer. Rather than mutating the entire `Parcel` as an unstructured byte array—which would corrupt the structure and cause rejection at the deserialization barrier—the mutator targets the specific data types identified during the DGIE phase.

NASS implements type-aware mutators for 23 distinct Binder argument types [3]. The fuzzer applies semantics-aware mutations tailored to each type:
*   **Primitive Integers and Floats:** Mutated using boundary-value heuristics (e.g., maximum values, zero, or negative numbers) to stress standard size validations.
*   **Strings:** Subjected to length expansions, malformed encodings, and special character insertions.
*   **Vectors (Arrays):** Undergo structural size mutations, dynamically adding or removing elements while preserving the overall `Parcel` validity.
*   **Special Object Types (FileDescriptors and StrongBinders):** For arguments requiring file descriptors, NASS writes fuzzed data to a temporary file and serializes the descriptor. For `StrongBinder` callbacks, NASS serializes a handle to a bespoke, fuzzer-controlled service, simulating inter-process callback loops.

The fuzzer dispatches a mutated `Parcel`, collects the isolated coverage bitmap, and analyzes the execution trace. If a mutated input bypasses a validation check and executes a previously unobserved basic block, NASS flags the input as valuable. It adds the input to the seed corpus and prioritizes subsequent mutations on exploring that newly discovered execution branch.

## 6.4 Real-World Case Studies and Discovered Vulnerabilities

The efficacy of combining dynamic interface extraction with isolated, grey-box coverage is demonstrated by empirical results. Deployed against 316 proprietary services across five modern COTS devices, NASS discovered 12 unique memory-corruption vulnerabilities, resulting in the assignment of five CVEs [3].

A notable example is the discovery of a **Heap Buffer Overflow in the Samsung S23 `vendor.samsung.hardware.radio.network` service**. 

Through DGIE probing, NASS dynamically unrolled a complex nested network message structure within the proprietary radio HAL, determining that the `Parcel` required a sequence of seven distinct deserializers. One of these fields was a signed integer representing the payload length.

Because the interface was accurately mapped, NASS's coverage-guided fuzzing engine progressed past the deserialization stub into the vendor's message dispatching logic. The proprietary service implemented a bounds check to ensure the payload length did not exceed the maximum buffer size prior to initiating a memory copy. However, the bounds check was implemented using a signed comparison:

```cpp
int32_t payload_length = parcel->readInt32(); 

// Flawed bounds check: bypassable with a negative integer
if (payload_length > MAX_MESSAGE_SIZE) {
    return ERROR_BUFFER_TOO_LARGE;
}

memcpy(internal_heap_buffer, data_ptr, payload_length);
```

By correlating coverage changes with input mutations, the evolutionary algorithm identified that mutating the `payload_length` to a negative value bypassed the conditional check, triggering new basic-block coverage. Because `memcpy` expects an unsigned `size_t` parameter, passing a negative integer resulted in an extensive, out-of-bounds memory copy, precipitating a highly exploitable heap overflow.

Furthermore, NASS identified sophisticated logical state vulnerabilities. On the Pixel 9, NASS uncovered a critical **Use-After-Free (UAF)** vulnerability in the `android.hardware.radio.sap.ISap` service (CVE-2024-47040). 

The service maintained a linked list of active requests, identified by unique tokens provided as RPC arguments. Upon request completion, the service traversed the list and freed the corresponding memory. Generating structurally valid `Parcels` containing specific token arguments allowed the evolutionary loop to explore edge cases in token handling. The fuzzer dispatched two consecutive requests utilizing identical tokens. The proprietary service failed to verify duplicate tokens, causing it to free an active request while it was concurrently processed by another thread, resulting in an exploitable UAF. 

These discoveries underscore the capabilities of modern fuzzing methodologies. Vulnerabilities situated deep within proprietary, closed-source HAL services—protected by complex IPC interfaces and obscured by multi-threaded execution noise—were automatically identified. By systematically reconstructing interfaces dynamically and guiding execution with isolated feedback, NASS demonstrates the feasibility of comprehensively auditing the proprietary barriers within modern mobile devices.
