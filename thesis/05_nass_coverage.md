# Chapter 5: NASS and Grey-Box Coverage in Multi-Threaded Daemons

Figuring out the interface definition of a proprietary HAL service using DGIE gets us past the structural "front door." However, simply knowing how to build a valid Binder `Parcel` isn't enough to find deep vulnerabilities. As system services get more complex, black-box generation approaches start to lose their edge. To actually navigate the deep, stateful logic hiding behind the deserialization stub, a fuzzer needs evolutionary guidance. It needs to see which code paths its inputs trigger and "reward" the mutations that push deeper into the binary's logic.

This evolutionary loop absolutely depends on getting accurate code coverage feedback. But when we're talking about Android native system services, collecting this feedback introduces a monumental engineering headache: the concurrency problem. This chapter looks at how NASS solves this issue, bringing precise, grey-box fuzzing to multi-threaded Android daemons.

## 5.1 The Concurrency Problem in Android System Services

Traditional grey-box fuzzers, like AFL, operate on a pretty simple assumption: the fuzzer spawns a single target process, feeds it a single input, and records whatever coverage gets generated by that one execution thread. 

Android system services completely break this assumption. A daemon like `cameraserver` or a vendor's camera HAL doesn't just sit there in isolation waiting for a fuzzer. It is a highly concurrent, multi-threaded process that is constantly running in the background. At any given millisecond, the service might be handling legitimate Binder requests from the Android framework, processing background hardware interrupts, or running internal maintenance routines.

If a fuzzer just naively slapped a coverage tracker onto the entire HAL service process, the resulting coverage map would be completely flooded with execution "noise." The fuzzer wouldn't be able to tell which basic blocks were executed because of its specially crafted fuzzing payload, and which blocks were just executed by some random background thread handling normal OS traffic. This pollution destroys the evolutionary algorithm's ability to link specific input mutations to specific code paths, making coverage guidance basically useless.

## 5.2 Thread-Localized Tracing via Dynamic Binary Instrumentation

To get clean, useful coverage data, the fuzzer has to isolate its own execution footprint from the background noise of the system. NASS does this through a highly surgical application of Dynamic Binary Instrumentation (DBI) using the Frida framework—specifically tapping into the Frida Stalker engine.

NASS's coverage architecture ties instrumentation directly to the mechanics of Binder IPC, taking advantage of the Single Entry Point (Si) RPC principle. Conceptually, the isolation logic works something like this:

```cpp
// Conceptual representation of NASS's Frida Hook on the Target Service

void nass_onTransact_hook_enter(void* thread_context, IPCThreadState* ipc_state) {
    // 1. Inspect kernel-provided caller credentials
    pid_t caller_pid = ipc_state->getCallingPid();
    
    // 2. PID-Based Caller Isolation
    if (caller_pid == NASS_FUZZER_CLIENT_PID) {
        // This transaction originates from the fuzzer.
        // 3. Activate Frida Stalker exclusively on this executing thread.
        FridaStalker_Start(thread_context);
        record_coverage = true;
    } else {
        // This is legitimate background OS traffic.
        // Do nothing. Allow normal execution without instrumentation overhead.
        record_coverage = false;
    }
}

void nass_onTransact_hook_exit(void* thread_context) {
    if (record_coverage) {
        // 4. Synchronous Capture and Termination
        FridaStalker_Stop(thread_context);
        export_coverage_bitmap_to_fuzzer();
    }
}
```

By filtering on the PID, NASS guarantees that the coverage bitmap fed back to the evolutionary engine is perfectly isolated. It represents *only* the synchronous, deterministic execution path triggered by the fuzzer's input, completely free from any multi-threaded background noise.

## 5.3 The Evolutionary Fuzzing Feedback Loop

With the interface dynamically mapped via DGIE and isolated coverage collection achieved via PID-filtered Stalker tracing, NASS finally has all the pieces in place for a robust evolutionary fuzzing loop.

NASS uses an interface-aware mutator built on top of LibFuzzer. Instead of just mutating the entire `Parcel` as a raw byte array—which would almost certainly corrupt the structure and cause the input to get bounced at the deserialization barrier—the mutator targets the specific data types it found during DGIE. 

NASS implements type-aware mutators for 23 different Binder argument types [3]. The fuzzer applies intelligent, semantics-aware mutations tailored to each type:
*   **Primitive Integers and Floats:** Mutated using boundary-value heuristics (like swapping in MAX_INT, 0, or negative values) to stress test standard size validations.
*   **Strings:** Subjected to length expansions, malformed UTF encodings, and special character insertions.
*   **Vectors (Arrays):** Undergo structural size mutations, adding or removing elements dynamically while ensuring the overall `Parcel` layout remains perfectly valid.
*   **Special Object Types (FileDescriptors and StrongBinders):** For arguments that require file descriptors, NASS writes fuzzed data to a temporary file and serializes the descriptor. For `StrongBinder` callbacks, NASS transparently serializes a handle to a bespoke, fuzzer-controlled service, effectively simulating complex inter-process callback loops.

The fuzzer dispatches a mutated `Parcel`, collects the isolated coverage bitmap, and analyzes the results. If a mutated integer causes the target service to bypass an `if (length > MAX_ALLOWED)` check and execute a completely new basic block, NASS flags this input as valuable. It adds the input to the corpus and focuses its next round of mutations on exploring that new execution branch.

## 5.4 Real-World Case Studies and Discovered Vulnerabilities

The real proof of combining dynamic interface extraction with isolated, grey-box coverage comes from the real-world results. When the researchers deployed NASS against 316 proprietary services across five modern Commercial Off-The-Shelf (COTS) devices (including the Google Pixel 9, Samsung Galaxy S23, and OnePlus 12R), NASS discovered 12 unique memory-corruption vulnerabilities, resulting in five assigned CVEs [3].

A great example is the discovery of a **Heap Buffer Overflow in the Samsung S23 `vendor.samsung.hardware.radio.network` service**. 

Using DGIE probing, NASS dynamically unrolled a highly complex nested network message structure inside the proprietary radio HAL. It figured out that the `Parcel` required a specific sequence of seven distinct deserializers. One of these reads was an integer representing the payload length.

Because the interface was perfectly mapped, NASS's coverage-guided fuzzing engine easily pushed past the deserialization stub and into the vendor's message dispatching logic. The proprietary service actually contained a safety check to ensure the payload length didn't exceed the maximum buffer size before triggering a memory copy. 

Crucially, though, the developer implemented a *signed* check:

```cpp
// Flawed proprietary logic discovered by NASS
int32_t payload_length = parcel->readInt32(); // Read recovered via DGIE

// Flawed bounds check: bypassable with a negative integer
if (payload_length > MAX_MESSAGE_SIZE) {
    return ERROR_BUFFER_TOO_LARGE;
}

// Heap Buffer Overflow triggered during memcpy
memcpy(internal_heap_buffer, data_ptr, payload_length);
```

By tying coverage changes back to input mutations, the evolutionary algorithm quickly realized that mutating the `payload_length` integer to a negative value successfully bypassed the `if` block, triggering new basic-block coverage. Because `memcpy` expects an unsigned `size_t` parameter, passing that negative integer resulted in an enormous, out-of-bounds memory copy. This crashed the service and created a highly exploitable heap overflow.

Beyond simple boundary checks, NASS also found sophisticated logical state flaws. On the Pixel 9, NASS uncovered a critical **Use-After-Free (UAF)** vulnerability in the `android.hardware.radio.sap.ISap` service (assigned CVE-2024-47040). 

The service maintained a linked list of active requests, identified by a unique token provided as an RPC argument. When a request finished, the service traversed the list and freed the corresponding memory. Because NASS was generating structurally valid `Parcels` containing these specific token arguments, its evolutionary loop explored edge cases in the token-handling logic. The fuzzer ended up dispatching two consecutive requests with the *exact same token*. The proprietary service didn't check for duplicate tokens, causing it to free an active request while it was still being processed by another thread, resulting in an exploitable UAF. 

These discoveries really highlight how far the field has come. Vulnerabilities buried deep inside proprietary, closed-source HAL services—guarded by complex IPC interfaces and hidden in multi-threaded execution noise—were automatically discovered. By systematically reverse-engineering the interface dynamically and guiding execution with isolated, PID-filtered feedback, NASS proves that the proprietary barriers protecting modern mobile devices can absolutely be dismantled.
