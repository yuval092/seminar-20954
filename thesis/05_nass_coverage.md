# Chapter 5: NASS and Grey-Box Coverage in Multi-Threaded Daemons

Determining the interface definition of a proprietary HAL service via DGIE resolves the initial structural barrier. However, constructing a valid Binder `Parcel` is insufficient for discovering deep vulnerabilities. As system services increase in complexity, black-box generation approaches lose their effectiveness. To navigate the stateful logic beyond the deserialization stub, a fuzzer requires evolutionary guidance. It must observe which code paths its inputs trigger and "reward" mutations that penetrate deeper into the application logic.

This evolutionary process relies heavily on accurate code coverage feedback. In the context of Android native system services, collecting this feedback presents a significant engineering challenge: the concurrency problem. This chapter examines how NASS addresses this issue, enabling precise, grey-box fuzzing within multi-threaded Android daemons.

## 5.1 The Concurrency Problem in Android System Services

Traditional grey-box fuzzers, such as AFL, typically operate under a simple premise: the fuzzer spawns a single target process, supplies a single input, and records the coverage generated by that execution thread. 

Android system services violate this assumption. A daemon like `cameraserver` or a vendor's camera HAL is a highly concurrent, multi-threaded process running continuously. Simultaneously, the service may be processing legitimate Binder requests from the Android framework, handling background hardware interrupts, or executing internal maintenance routines.

If a fuzzer indiscriminately applied a coverage tracker to the entire HAL service process, the resulting coverage map would be inundated with execution "noise." The fuzzer could not distinguish between basic blocks executed due to its specific payload and those executed by background threads handling normal OS traffic. This pollution compromises the evolutionary algorithm's ability to correlate specific input mutations with specific code paths, rendering coverage guidance ineffective.

## 5.2 Thread-Localized Tracing via Dynamic Binary Instrumentation

To acquire clean coverage data, the fuzzer must isolate its execution footprint from the system's background noise. NASS achieves this through surgical application of Dynamic Binary Instrumentation (DBI) using the Frida framework, specifically the Frida Stalker engine.

NASS's coverage architecture links instrumentation directly to the mechanics of Binder IPC, leveraging the Single Entry Point (Si) RPC principle. The isolation logic functions as follows:

```cpp
// Conceptual representation of NASS's Frida Hook on the Target Service

void nass_onTransact_hook_enter(void* thread_context, IPCThreadState* ipc_state) {
    // 1. Inspect kernel-provided caller credentials
    pid_t caller_pid = ipc_state->getCallingPid();
    
    // 2. PID-Based Caller Isolation
    if (caller_pid == NASS_FUZZER_CLIENT_PID) {
        // This transaction originates from the fuzzer.
        // 3. Activate Frida Stalker exclusively on this thread.
        FridaStalker_Start(thread_context);
        record_coverage = true;
    } else {
        // This is normal background OS traffic.
        // Do nothing. Allow execution without instrumentation overhead.
        record_coverage = false;
    }
}

void nass_onTransact_hook_exit(void* thread_context) {
    if (record_coverage) {
        // 4. Synchronous Capture and Termination
        FridaStalker_Stop(thread_context);
        export_coverage_bitmap_to_fuzzer();
    }
}
```

This approach ensures that the coverage bitmap returned to the evolutionary engine is isolated. It represents solely the synchronous, deterministic execution path triggered by the fuzzer's input, eliminating multi-threaded background noise.

## 5.3 The Evolutionary Fuzzing Feedback Loop

With the interface dynamically mapped via DGIE and isolated coverage collection achieved through PID-filtered Stalker tracing, NASS establishes a robust evolutionary fuzzing loop.

NASS employs an interface-aware mutator built upon LibFuzzer. Rather than mutating the entire `Parcel` as a raw byte array—which would likely corrupt the structure and cause rejection at the deserialization barrier—the mutator targets the specific data types identified during DGIE. 

NASS supports distinct mutation strategies for 23 different Binder argument types [3]. The fuzzer applies semantics-aware mutations tailored to each:
*   **Primitive Integers and Floats:** Modified using boundary-value heuristics (e.g., inserting MAX_INT, 0, or negative values) to test standard size validations.
*   **Strings:** Subjected to length alterations, malformed UTF encodings, and special character insertions.
*   **Vectors (Arrays):** Undergo structural size mutations, dynamic element addition or removal, while ensuring the overall `Parcel` layout remains valid.
*   **Special Object Types (FileDescriptors and StrongBinders):** For arguments requiring file descriptors, NASS writes fuzzed data to a temporary file and serializes the descriptor. For `StrongBinder` references (often used for callbacks), NASS transparently serializes a handle to a bespoke, fuzzer-controlled service, simulating complex inter-process callback mechanisms.

The fuzzer dispatches a mutated `Parcel`, collects the isolated coverage bitmap, and analyzes the results. If a mutated integer allows the target service to bypass an `if (length > MAX_ALLOWED)` check and execute a new basic block, NASS flags the input as valuable. It adds the input to the corpus and focuses subsequent mutations on exploring that newly discovered execution branch.

## 5.4 Real-World Case Studies and Discovered Vulnerabilities

The efficacy of combining dynamic interface extraction with isolated, grey-box coverage is demonstrated by real-world results. When deployed against 316 proprietary services across five modern Commercial Off-The-Shelf (COTS) devices (including the Google Pixel 9, Samsung Galaxy S23, and OnePlus 12R), NASS discovered 12 unique memory-corruption vulnerabilities, yielding five assigned CVEs [3].

A notable example is the discovery of a **Heap Buffer Overflow in the Samsung S23 `vendor.samsung.hardware.radio.network` service**. 

Utilizing DGIE probing, NASS dynamically unrolled a complex nested network message structure within the proprietary radio HAL. It determined that the `Parcel` required a specific sequence of seven distinct deserializers, one of which was an integer representing the payload length.

With the interface mapped, NASS's coverage-guided engine navigated past the deserialization stub into the vendor's message dispatching logic. The proprietary service included a check to ensure the payload length did not exceed the maximum buffer size prior to initiating a memory copy. 

However, the implementation utilized a *signed* check:

```cpp
// Flawed proprietary logic discovered by NASS
int32_t payload_length = parcel->readInt32(); // Read recovered via DGIE

// Flawed bounds check: bypassable with a negative integer
if (payload_length > MAX_MESSAGE_SIZE) {
    return ERROR_BUFFER_TOO_LARGE;
}

// Heap Buffer Overflow triggered during memcpy
memcpy(internal_heap_buffer, data_ptr, payload_length);
```

By correlating coverage changes with input mutations, the evolutionary algorithm determined that mutating the `payload_length` integer to a negative value bypassed the `if` block, triggering new basic-block coverage. Because `memcpy` expects an unsigned `size_t` parameter, the negative integer resulted in an extensive, out-of-bounds memory copy, crashing the service and creating an exploitable heap overflow.

In addition to boundary checks, NASS identified sophisticated logical state flaws. On the Pixel 9, NASS uncovered a critical **Use-After-Free (UAF)** vulnerability in the `android.hardware.radio.sap.ISap` service (assigned CVE-2024-47040). 

This service maintained a linked list of active requests, identified by a unique token provided as an RPC argument. Upon completion of a request, the service traversed the list and freed the corresponding memory. Because NASS generated structurally valid `Parcels` containing these specific token arguments, its evolutionary loop explored edge cases in the token-handling logic. The fuzzer dispatched two consecutive requests with the *exact same token*. The proprietary service failed to check for duplicate tokens, causing it to free an active request while it was still being processed by another thread, resulting in an exploitable UAF. 

These discoveries demonstrate the capability to automatically identify vulnerabilities within proprietary, closed-source HAL services, guarded by complex IPC interfaces and obscured by multi-threaded execution noise. By systematically reverse-engineering the interface dynamically and guiding execution with isolated, PID-filtered feedback, NASS illustrates that the proprietary barriers protecting modern mobile devices can be effectively analyzed.
